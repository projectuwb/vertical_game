# DECISIONS

Every choice made that the specs did not settle. One line each, no discussion,
no waiting for approval.

Format:
`- [YYYY-MM-DD] <decision> — <one-clause reason>`

- [2026-08-07] `npm run sim`/`npm run perf` compile via a dedicated `tsconfig.cli.json` (NodeNext) + plain `node`, not `tsx` — keeps devDependencies to exactly the `TECH_SPEC.md` §2 list.
- [2026-08-07] Vitest runs in the `node` test environment, not `jsdom` — `/sim` and `/meta` (the tested code) are headless by rule, and `jsdom` isn't in the §2 dependency list.
- [2026-08-07] Desktop hold-to-Flourish is bound to the Space key — GAME_DESIGN.md §3 requires a keyboard hold-to-Flourish input but doesn't name a key, and Space is the least likely to collide with A/D/arrow movement.
- [2026-08-07] Drifter's lateral strafe speed is set to 4 u/s (40% of its forward speed) — GAME_DESIGN.md §8.1 says it "strafes laterally" without a number; fast enough to force leading shots, slow enough not to look erratic.
- [2026-08-07] Projectile-vs-Blot hit radius set to 0.6u — neither spec models collision as circle-vs-circle explicitly; chosen larger than a Blot's silhouette but smaller than the Line's 0.85u row spacing so hits feel fair without adjacent-row false positives.
- [2026-08-07] The runner-joins-the-back animation (GAME_DESIGN.md §7.1) travels for 0.6s — not given a number in the spec; reads as a clear run without lagging, comfortably inside Task 2.5's 1.2s acceptance bar.
- [2026-08-08] Sealstack HP set to 60, hit-depth to 1.0u — GAME_DESIGN.md §7.3 gives the impact-loss formula but not the stack's own HP or collision thickness; 60 asks for sustained fire (comparable to a Crust) without being a boss fight.
- [2026-08-08] A Sealed gate's revealed effect can combine an arithmetic op with a conversion (GAME_DESIGN.md §7.2's "gate maths order: multiply before add within a single gate; conversion applies after count changes" only has observable meaning if a single gate can carry both) — plain Arithmetic/Conversion/Temper gates stay single-effect; the compound path exists specifically for Sealed's reveal table and is what makes the ordering rule testable.
- [2026-08-08] Gate-pair archetype mix set to 20% Sealed-vs-modest / 30% safety-valve / 50% explicit dilemma — GAME_DESIGN.md §7.2 only states the ≥1-in-4 dilemma floor, not how pairs are chosen; this mix satisfies it with comfortable margin (~70% actual dilemma rate).
- [2026-08-08] The Spawn Director's Slip-budget spend order (planSlipSpawn: a Banner if the budget fully covers it, then a 30%-chance +5 single/pair, otherwise a +1 run sized to the remaining budget) is this implementation's choice — GAME_DESIGN.md §9 gives the HP-budget-per-100u formula but not how it's spent across the three Slip variants. This is exactly what Task 4.6's balance pass will tune.
- [2026-08-08] Gate pairs spawn every ~220u with ±10% jitter (matching "roughly every 220u"); Sealstacks spawn roughly every 500u — GAME_DESIGN.md §7.3 gives no Sealstack cadence at all, so this is a placeholder frequency for Task 4.6 to tune.
- [2026-08-08] Firing has no auto-aim: a projectile's x is fixed at spawn to its muzzle's formation-slot x and never adjusts toward a target — confirmed as intentional, not a bug, by GAME_DESIGN.md §8.1's Drifter entry ("forcing you to lead your shots"), which only makes sense if the player (via Brush lateral position) is the one doing the aiming. Two `world.test.ts` cases were spawning targets at a fixed x with a stationary Brush and expecting near-certain hits despite only 1-in-`rowSize` muzzles lining up; fixed by giving them the travel distance a real wave/verge would (spawnDistanceU / within-range) rather than changing the firing model.
- [2026-08-08] Unshot Slips now despawn once they scroll `missDespawnMarginU` (2u) past the Brush, rather than persisting at ever-more-negative z forever — found while building the Task 2.7 harness: `pools.slipCapacity` (64) is far smaller than the Slip volume a multi-minute Passage offers (a run every ~100u of travel, up to 14 Slips per run), so without despawn, ignoring even a modest fraction of runs silently exhausts the pool partway through every long Passage and Slip spawning just stops. GAME_DESIGN.md §7.1 already establishes "missing them costs nothing"; it just never says the miss has to free the slot.
- [2026-08-08] `npm run sim`'s `--sweep` flag parses but doesn't actually override `BALANCE` yet — `BALANCE` is a deeply frozen singleton (Task 1.6's own acceptance test asserts this) imported directly by every `/sim` file, so a real sweep needs a config-injection path threaded through `createWorld`/`stepWorld`, not a CLI-level hack that would either break the freeze invariant or silently do nothing. That plumbing is exactly Task 4.6's job ("sweep the director and Slip budget until every target passes"); for now `--sweep` runs the unmodified baseline and says so in the report.
- [2026-08-08] `BALANCE_REPORT.md`'s §11 target table reports N/A (not a fabricated pass/fail) for every target whose prerequisite doesn't exist yet: Seals (Task 3.x), the Inkstone/upgrades (Task 4.2), and per-Blot-class death attribution (no `/sim` code currently records which Blot class caused a contact death, only that "blot" was the cause) — building that instrumentation belongs with Task 4.6's real balance pass, not Task 2.7's harness scaffold.
- [2026-08-08] Ink pool hit radius set to 1.2u (wider than the 0.6u projectile hit radius, since it's the Brush's own footprint driving over a puddle, not a pinpoint shot) and pools spawn within 85% of the lane half-width — neither given a number in GAME_DESIGN.md §6.
- [2026-08-08] A Flourish hold that begins while still on cooldown is treated the same as one that begins under `minWetnessToCharge`: the charge is invalid for that whole hold (meter pulses, release does nothing) rather than becoming valid partway through if the cooldown expires mid-hold — GAME_DESIGN.md §6 only specifies the Wetness-insufficient case ("holding while at <40 Wetness does nothing but shows the meter pulsing"), not cooldown-during-hold; treating them identically is simpler and avoids a hold that starts "pulsing" silently turning into a real charge.
- [2026-08-08] Flourish's "deletes all Blot projectiles on screen" clause is a no-op for now — no `/sim` code currently models a Blot-side projectile (Blotter's ink lob is a direct instant hit in `blot.ts`'s `updateBlotMotion`, not a pooled in-flight entity). If a future task gives Blotter a real lobbed projectile, Flourish should delete those too; `flourish.ts`'s `applyFlourishSweep` docblock flags this so it isn't forgotten.
- [2026-08-08] All five harness bot strategies now pause firing (hold, without regard to whether it forms a valid Flourish charge) once Wetness drops to 10, resuming once it climbs back to 60 — none of TECH_SPEC.md §6's strategy descriptions predate Task 2.8's Wetness economy, so without this every bot fires continuously, hits 0 Wetness within ~17s of Passage start, and stays there (never holding to let it recover) for the rest of every run, permanently halving its own fire rate and badly skewing every balance number. This is a shared "don't run dry forever" instinct, not a per-strategy behavior — the actual aim/targeting logic is untouched.
- [2026-08-08] The three Phrase attacks apply their damage as an instant hit-test rather than genuinely travelling/persisting entities, except where the spec explicitly requires persistence: Hane's Scatter hits the nearest `scatterCount` Blot in a forward cone in one step; Tome's Press hits everything already inside its full `pressWidthU`×`pressTravelU` corridor in one step (GAME_DESIGN.md §4 gives no travel speed for the "shockwave," and a genuinely travelling entity would need a new pooled type with its own motion/collision — scope no other Phrase needs); Harai's Sweep, the one Phrase explicitly described as "sustained," *is* modelled as persisting for its full 0.5s, ticking damage 10×/s via a small accumulator rather than instantly.
- [2026-08-08] `tsconfig.cli.json` now includes `"dom"` in `lib` — `npm run build:cli` was failing (TS2304 on `requestAnimationFrame`/`HTMLElement`/`Document`) the first time anything actually tried to compile it: `"include": ["src/core", ...]` pulls in all of `core/loop.ts` (the browser `FixedStepLoop`) regardless of what the harness itself imports, and `lib: ["ES2022"]` alone has no DOM types. `npm run verify` never runs `build:cli`, so this had gone uncaught since Task 1.1. The CLI harness never instantiates `FixedStepLoop` or calls its DOM-touching methods, so this is a type-only fix with no runtime exposure to a document that doesn't exist in Node.
